First local run

Start on a configured Linux deployment with a small regression unit. The following option file uses Open64 compilers supplied by the site; replace /opt/open64/bin with the actual installation. Save it outside the source tree as local.opt:

export CTI_GROUPS="$CTI_HOME/cti_groups"
export SELECTIONS="Regression/fe"
export CC=/opt/open64/bin/opencc
export CXX=/opt/open64/bin/openCC
export FC=/opt/open64/bin/openf90
export DATA_MODE=+DD64
export DATA_MODE_MAPPING="+DD32/-m32 +DD64/-m64"
export CTI_OPT_SIGN="-"
export OPT_LEVEL=2
export CTI_COMPILE_HOST_OS=Linux
export CTI_RUN_HOST_OS=Linux
export CTI_REPORT_PASSES=true
export CLEAN=false

CTI_HOME must resolve to the configured installation, and the selected compilers must be executable. The defaults deliberately set CC, CXX, and FC to /bin/false. Unit settings may further customize options; inspect the generated compile command before assuming your chosen flags reached a test.

From a separate scratch directory, set your installation path and inspect the effective run environment:

export CTI_HOME=/absolute/path/to/opencti
perl "$CTI_HOME/bin/TM.pl" -nod -nomail -f ./local.opt \
  -w "$PWD/fe.work" -l "$PWD/fe.log" test_setting

test_setting prints the full environment and exits before running drivers. Avoid sharing its output without reviewing it for credentials inherited from the shell. It still loads option files, checks selections/paths, and can create the log's parent directory.

Run the selected unit:

perl "$CTI_HOME/bin/TM.pl" -nod -nomail -f ./local.opt \
  -w "$PWD/fe.work" -l "$PWD/fe.log" run

run replaces a previous work directory: it moves it to a .clean sibling and removes that directory asynchronously. Use a fresh work/log location for runs you want to retain. CLEAN=false preserves driver artifacts; it does not disable this top-level replacement.

TM command reference

The parser in TM.pl accepts these options. Its built-in help contains historical discrepancies listed below.

OptionImplemented purpose
-f FILELoad a shell options file after defaults
-xf FILELoad another shell options file after -f
-px NAME=valueSet an environment variable after defaults, before the user options file
-x NAME=value or NAME=valueSet an environment variable after option files and CLI-derived adjustments
-nodRequest local execution
-dRequest distributed execution
-d=POOL:host1,host2Request distributed execution with a pool/host restriction
-w DIR, -l FILESet work directory and summary log
-id NAMESet NAME.work and NAME.log; explicit -w/-l take precedence regardless of argument order
-nomailDisable final log mail unless subsequently overridden by -x SEND_LOG=...
-m true, -m false, -m USERChoose final log recipients; absent a choice, mail defaults to the invoker
-skip FILERead whitespace-separated fully qualified skip selections
-sSort units using recorded timing information
-cDisable data-mode validation
-env DIRSet TEST_ENV_DIR before loading defaults; defaults may overwrite it
-native, -crossApply historical IPF/PA simulator settings; do not use these as generic x86 switches
-h, -helpPrint usage and exit with status 1

The accepted subcommands are run, clean, and test_setting. With no subcommand the code selects run. clean is parsed but has no standalone action in the dispatch loop; cleanup happens inside run. The help text's claim that the default is clean run does not match the implementation.

The script ends with exit 0 after a completed run even when tests fail. Check the summary log and per-test results rather than treating the TM process exit code as the test verdict. Fatal infrastructure errors may still terminate the process earlier.

Select and narrow tests

SELECTIONS names groups or units relative to CTI_GROUPS. Select a unit using SELECTIONS="Regression/fe"; use TESTS to narrow regression tests to exact unqualified test filenames, including extensions:

perl "$CTI_HOME/bin/TM.pl" -nod -nomail -f ./local.opt \
  -x 'TESTS=bug15191_4.c' -x 'SELECTIONS=Regression/cg' \
  -w "$PWD/one.work" -l "$PWD/one.log" run

Groups expand through CHILDREN in their tmconfig. SELECTIONS=.all. requires root CHILDREN configuration; this checkout has no cti_groups/tmconfig, so explicitly select Regression and/or Applications instead. A single source path is not a unit selection. See configuration.

Artifacts and triage

The summary log records totals and groups failures by the labels in the result catalog. Unit work directories appear under the run's work tree. Names vary by driver and iteration, but useful artifacts include:

ArtifactUse
*.envSaved options and environment used by generated scripts
*.compile.sh, *.comp.errRecompile script and compile/link diagnostics
*.run.sh, *.run.outRuntime reproduction script and captured program output
*.resultInternal result tag, such as CompileErr or DiffPgmOut
compare.resultsApplication validation status; present and empty for success
TMmsgs/Messages collected to build the summary log

Read each generated script, change to its working directory, and run it with the configured shell. Keep its .env file and referenced source paths available. Recompiling or rerunning can overwrite artifacts, so copy the failure directory first if you need the original evidence.

Reruns and work-directory reuse

The FT12 experiment records actual rerun preview/launch behavior. A preview creates rerun.<pid>.opt but executes no test; launch acknowledgement is separate from test completion. The CGI puts rerun work/log/options under the original work directory, so reusing that parent path can delete all of them even with CLEAN=false. Archive original and rerun evidence outside that execution hierarchy before reuse.

Compare the original invocation and captured effective settings with the generated rerun command. The current header can omit -x, -px and the extra -xf file; the actual FT12 rerun loses a compiler flag and changes DiffPgmOut into CompileErr. Pool/view/source/master context and option differences must be explicit. Newly allocated native attempts must have distinct IDs and non-overlapping workspaces; changed debugging sessions and deliberate legacy reuse controls retain separate provenance.

Reopening with unavailable prerequisites

Check the actual interpreter, ELF loader, saved .env, source links, compiler/runtime/input/comparator and baseline before replay. The FT13 experiment finds that an existing script can fail kernel lookup because its interpreter/loader is absent, while a missing or dangling .env can still allow the saved run phase to return zero. Neither a script pathname, image ID nor process status alone proves a complete environment.

Record missing roles and explicit reprovisioning references separately from the original test verdict. Verify matching captured content or compatible authorized access after restoration, then execute and record the phase. Credential references belong in evidence; credential values do not. FT13 exercises local synthetic provisioning and offline image restoration without changing the framework; production secret/resource integrations and historical imports remain separate acceptance work.

Open an interactive captured workspace

The new session CLI opens supported captured failures in private Docker workspaces without changing the legacy framework or original evidence. Run ./tools/cti-session open --capture validation/phase0/legacy/evidence/ft09-001 from your terminal. It restores captured paths, enters the test directory and loads its saved .env. Use list, attach, exec, stop and remove for the private session lifecycle.

On macOS, the optional tools/cti-dashboard adapter connects registered failed-case links to a new Terminal window and the same CLI opener. The guide covers local capture pages, opt-in legacy CGI setup, original-log identity checks and rollback. Each click creates a fresh private session while retaining the original capture and result.

For future remote/GPU execution, distinguish collection completeness from compatible replay readiness. The FT14 isolated subset retains a worker's original job identity and verifies native inspection after worker cleanup, but no compatible remote GPU host is available. GPU requests stay blocked without CPU fallback. Its successful saved-phase replay is an explicitly separate CPU transport control; the dashboard and CLI have not gained a remote/GPU backend through this experiment.

Application and externally scripted failures need their own harness closure. The FT15 results verify application compile/validation recipes, upstream make check inputs and markers, plus script invoker/comparison recipes, glue, file/directory inputs and masters. Preserve their configuration and generated scripts as well as .env: exit-check settings can be pruned from the environment but embedded in recipes. The script driver uses RUN_TESTS_CHECK_EXIT and TESTS despite older metadata limiting their descriptions to regression tests. Script output is stdout followed by stderr, and collection runs outside the normal phase limiter. A stale empty application marker can mask a failed custom run hook; archive the original result first and do not infer successful validation from that marker alone.

For interrupted tests, keep the cancellation request, termination observation and acknowledgement separate. The FT16 results preserve original compile/run/compare recipes, environment, generated input and separate partial streams around an actual stock timeout and isolated cancellation. TM exit 0 can accompany LongExec; a killed TM or container has its own process status. Before-dispatch cancellation produces no recipes or runtime outputs. Reopening a worker-loss checkpoint is inspection of that original attempt, not permission to rerun automatically: missing final results remain explicit and preservation remains incomplete. Collect reachable state before deleting the workspace, and release reservations only after termination is confirmed. These fixture tools do not add a production cancellation command or qualify the dashboard control.

For case-distinct failures, keep the archive or manifest/objects on the Mac and expand them only into a verified case-sensitive worker filesystem. The FT17 results retain sample.C/sample.c, different masters, exact modes and link targets without renaming either test. The validation-only native materializer blocks an incompatible destination before writing. Executable bits matter: a saved run through a link chain reports ExecErr when the helper loses them, then runs after restoration in a private copy. The existing regression driver also shares work basenames after stripping extensions; capture each selected identity in a separate workspace when preserving same-stem tests. Running both in one unit can retain two result records but only the later recipe/object/executable/result files. FT17 documents that gap and leaves the framework unchanged.

Run-level loading order

TM.pl and tmUtilities.pl implement this sequence:

  1. Load global definitions while importing CTI_lib; already defined environment values are preserved by its definition loader.
  2. Establish host metadata and load conf/default.conf through Scripts/saveOpt2Env.
  3. Apply -px NAME=value assignments.
  4. Load the -f options file, if supplied.
  5. Load the -xf options file, if supplied.
  6. Apply CLI-derived work/log, distributed, mail, skip, and native/cross settings and host defaults.
  7. Apply -x NAME=value and bare NAME=value assignments.
  8. Select units; drivers subsequently apply group/unit/test customizations.

An unqualified -x OPT_LEVEL=2 wins at the run level, but a unit's tmconfig can still replace it later. Use a level-specific override when you need to override that unit's setting. Explicit -w and -l beat -id regardless of position; a final -x TEST_WORK_DIR=... or -x LOG=... can replace them again.

Selection and test discovery

CTI_GROUPS is the root containing Regression, Applications, and Perf. SELECTIONS contains whitespace-separated relative group/unit paths. A directory with Src/ is a unit. Other directories expand only through their CHILDREN configuration; simply creating a subdirectory does not enroll it in a group run.

The root .all. selection reads root CHILDREN, which is absent from this distribution. Use explicit groups. SKIP_SELECTIONS can exclude fully qualified groups, units, or regression tests. TESTS narrows regression tests by exact unqualified name.

collectTests.pm discovers sources using LANG_TYPE and EXT_TO_FE, plus explicit .list and tmconfig.list definitions. Sources belonging to multi-file tests are removed from the standalone test set. List-defined tests can be included regardless of the normal language filter.

Hierarchical customization

customizeOptions.pm walks the selected group/unit path from its outer group to its leaf. More specific levels can replace values from earlier levels. Regression tests then apply test-specific settings.

  • Group/unit files use NAME=value or NAME="value", without export. Keep comments on their own lines.
  • Unit tmconfig.env contains test-pattern: NAME=value records matched against a test base name.
  • Test files are Src/<test-base>.tmconfig, with the source extension stripped. Their settings take precedence over matching tmconfig.env entries.
  • Only names listed in conf/TestLevelCustomizableOptions.conf, and the recognized customization variants, are accepted in these files.

Level-specific environment names join path components with underscores. For example, to override OPT_LEVEL at Regression/apo, set:

export Regression_apo_OPT_LEVEL=2

At the same level, this environment value takes precedence over the tmconfig assignment. EXTRA_PRE_NAME and EXTRA_POST_NAME add text before/after an option rather than simply replacing it. Multi-iteration tests can use NAME_ITERATION_N and corresponding pre/post variants. Consult the implementation for the distinction between non-leaf accumulation and leaf expansion before creating complex combinations.

tmconfig values expand CTI_HOME and CTI_GROUPS; do not assume general shell variable expansion or shell evaluation. openFile.pm handles supported preprocessing. For examples of actual customizations, inspect the selected unit's files rather than copying obsolete target-specific flags.

The FT11 capture exposes a RUN_TESTS_NEG=true limitation: an unexpectedly zero-exit program can end as SuccessExec because the outer script overwrites ExecBadPass. Inspect expected and actual phase outcomes as well as the final tag. TM process exit zero also does not prove that tests passed or finished.

The generated catalog contains the complete declared test-level names and result types. Its descriptions are copied from the configuration metadata and can contain historical language. The configuration files remain authoritative for declared keys; driver code determines actual behavior.

conf/SavedOptions.conf adds environment names captured for reproduction. Test-level customizable options are also saved, except entries explicitly excluded by conf/UnsavedOptions.conf.

Layout and enrollment

cti_groups/
  Regression/
    tmconfig                 # CHILDREN and regression.pl selection
    myunit/
      tmconfig
      tmconfig.env           # optional pattern-specific settings
      tmconfig.list          # optional multi-source definitions
      Src/
        sample.c
        sample.tmconfig      # optional per-test settings
      Masters/
        sample.out
  Applications/
    tmconfig                 # CHILDREN and application.pl selection
    myapp/
      tmconfig
      Src/
        Makefile.CTI
        ...

A Src/ subdirectory identifies a unit. Add new units to the parent group's CHILDREN list for group-wide runs. A direct unit selection works without parent enrollment. Preserve filename case, especially C .c versus C++ .C.

Regression tests

The regression driver discovers individual sources by the configured extension/language mapping. Put a single-source test in Src/. Add its runtime master under the configured MASTER_FILE_PATH; Regression/tmconfig sets that path to ../Masters, relative to Src.

A minimal test that produces no output can use an empty master:

int main(void) { return 0; }

For sample.c, place an empty Masters/sample.out. CTI's regression output padding is enabled by default; set RUN_TESTS_PAD_OUTPUT=false in Src/sample.tmconfig when the master should contain only raw program output. Verify the captured output before accepting the master.

For a compile-only test, add RUN_TESTS=false to its .tmconfig; also set LINK_TESTS=false if no link step is intended. A negative compile test uses CT_NEG=true. To compare diagnostics, enable CT_DIFF=true and provide the appropriate .err master, or use ERROR_MASTER_EMPTY=true if an empty diagnostic master is intended.

For negative runtime tests, configure RUN_TESTS_NEG=true and runtime exit checking, then verify a deliberately unexpected zero exit as well as the expected rejection. The FT11 capture finds that the legacy outer script can overwrite ExecBadPass with SuccessExec when the run phase exits zero. A final pass alone is insufficient to validate this oracle.

For multi-source tests, create Src/<name>.list listing source files, or a unit-level tmconfig.list with records such as:

joined: first.c second.c

Inspect readListFile.pm for list syntax. collectTests.pm prevents these component sources from also running as independent tests.

Master names start with the test base name and the configured suffix (out or err by default). RUNTIME_OUTPUT_QUALIFIERS and ERROR_OUTPUT_QUALIFIERS can insert option values into the name. locateMaster.pm defines the lookup order and the special Fortran handling of the COMPILER_VERSION qualifier.

Use SELECTIONS for the unit and TESTS for a specific test filename. Run locally with CLEAN=false, inspect compile/link/run commands, and confirm that the intended failure or output comparison is exercised before adding it to broad selections.

Application wrapper contract

The application driver operates on one application unit, populates a work directory, customizes options, and generates scripts calling GNU make. Set the wrapper filename in the application's tmconfig:

MAKEWRAPPER=Makefile.CTI

The implementation adds -f only when MAKEWRAPPER is set. Otherwise GNU make uses its normal makefile discovery. There is no hardcoded M.hp.TAHOE default in this driver.

The normal compile stage invokes the make target compile; the normal execution stage invokes validate. A successful validation must return zero and leave compare.results present and empty. A missing file produces an execution failure; a nonempty file produces an output-difference failure. Separate run, compare, and clean targets are useful wrapper conventions; they are not each independently invoked by the normal two-stage driver path.

The driver passes CC, CXX, FC, AR, EXTRA_FLAGS, language-specific EXTRA_CFLAGS/EXTRA_CXXFLAGS/EXTRA_FFLAGS, EXTRA_LIBS, SIMULATOR, and GMAKEROOT when defined. EXTRA_FLAGS includes data-mode and optimization settings. Wrappers must actually forward those flags to the upstream build; assigning CC alone does not prove the compiler used the intended options.

A simple wrapper around a configure/make project can follow this pattern. Recipe indentation must be tabs:

export CC
export CFLAGS = $(EXTRA_FLAGS) $(EXTRA_CFLAGS)

compile:
	./configure
	$(MAKE) -f Makefile

validate:
	rm -f compare.results
	$(MAKE) -f Makefile check
	: > compare.results

clean:
	$(MAKE) -f Makefile clean

Only create the empty marker after validation succeeds. Remove stale markers first. A failed upstream check must propagate failure rather than being hidden by an unconditional successful command. For a real bundled example, see GSL's wrapper.

APPLICATION_SETUP_HOOKS customizes work-directory preparation. APPLICATION_RUN_HOOK supplies a script generator for specialized runs; it receives the unit name and output-script filename. Performance templates use this mechanism. Use the declared hooks and driver code to establish argument and exit-code contracts.

Import and dependencies

Import a clean source tree, not a previously built directory. Retain upstream notices and record any portability patches. Ensure configuration respects the selected compilers and flags, and arrange for tests to run without interactive input. Avoid fixed scratch filenames that collide across concurrent jobs. Set TIME_LIMIT to a justified value for larger builds.

The bundled application units are Applications/gsl-1.14 and Applications/hmmer-2.3.2; Perf/ex1 is a performance example. Dependencies come from each unit's wrapper and upstream source, not from a package dependency installer. Application runs also require the hardcoded Linux GNU make path described in installation.

Legacy add-test tools

TM.pl does not implement an add command. The older import tool is bin/www/addtest.pl, with a web form at www/cgi-bin/addtest.cgi. Its parser requires -CTI_GROUPS to specify the absolute test root. It includes SVN/ClearCase-oriented check-in helpers and is not a Git-aware replacement for editing a working tree. Use the manual layout workflow above for this Git checkout; review the tool's implementation and dry-run behavior before using it in a configured legacy repository.
