Host and tool requirements

There is no top-level compile/install target. Most CTI infrastructure runs directly as Perl or shell scripts; dTM includes Java classes and native load-monitor binaries. Test compilers and application dependencies are external.

ComponentRequirements visible in the code
Test manager and driversPerl; Unix tools; /bin/ksh for Scripts/saveOpt2Env; a compatible shell for generated scripts
Application driverLinux; GNU make at /usr/bin/gmake through bin/gmake; application-specific tools
Interactive configurationPerl modules HTML::Entities, HTTP::Request::Common, LWP::UserAgent, Mail::Internet, Mail::Util, XML::Simple; Java checked unconditionally
dTMJava runtime; Perl with XML::Simple; SSH or configured remote shell; working native load monitor on each worker; shared installation/results paths
Rebuilding dTMJDK for Java sources, C compiler and pthread support for loadd.c
Web interfaceCGI-capable web server, Perl CGI dependencies including CGI, PHP for dTMState.php
Optional dashboard-to-Terminal adapterPython 3 on the web service; macOS, Python 3.9+, Docker and the native URL handler on each developer's Mac
Documentation buildPython 3 standard library

The old README names Perl 5.8 and Linux/HP-UX. There is no current compatibility test matrix. The shipped bin/gmake explicitly rejects non-Linux hosts, and shell scripts contain [[ ... ]]; a generic POSIX /bin/sh is not sufficient for every path. macOS can be used to inspect the source and build these docs, but is not a verified test host.

Evidence: configuration checks, option loader, make wrapper, application driver.

Obtain a complete checkout

git clone https://github.com/open64-compiler/opencti.git
cd opencti

Use a case-sensitive filesystem. OpenMP validation tests contain pairs such as Test_omp_destroy_lock_C.C and Test_omp_destroy_lock_c.c; they cannot coexist in a case-insensitive working tree. A clone may finish with collision warnings and immediately show modified files. A Git archive retains both names, but extracting it onto the same filesystem does not solve the collision.

Choose an absolute installation path without spaces or shell metacharacters. Many infrastructure commands interpolate paths into shell command strings. For dTM, make the installation and test/results paths available at the same locations to the launcher and workers; align user identities and permissions across hosts. NIS and NFS were the original deployment choices, not mandatory named technologies in the local runner.

Configure a deployment copy

Keep an unconfigured checkout or backup before running the configurator. Run it from the repository root on the intended host:

perl configure.pl

The script prompts for the CTI path, administrator, dTM host/ports, Perl path, Java home/options, load-monitor port, remote-shell command, and web host/account/root. Defaults include dTM ports 6969 and 6968, load-monitor port 5010, and SSH at /usr/bin/ssh.

It checks the six Perl modules listed above and executes the selected Java binary. Its Java-version parser expects the historical java version "1.x..." format and compares the second version component against 5. A modern JDK may fail this check despite being newer. Do not interpret this check as proof of compatibility with modern Java; adapting it is a code change outside this documentation rebuild.

The substitution list in configure.pl includes:

  • conf/default.conf, lib/CTI_global.env, and dTM environment/XML files.
  • Regression and performance option/schedule templates.
  • Web scripts and selected older documentation files.

It replaces literal configuration tokens in place. A second run does not replace values whose tokens were already consumed. Selecting a different Perl path also recursively rewrites occurrences of /usr/local/bin/perl in text files. The default user web root can create a public_html/CTI symlink in the configuring user's home directory.

Check the relevant configuration files afterward:

rg -n '\{CONFIGURE_' conf lib dtm/conf dtm/lib cti_regression cti_perf

Review matches; inactive comments and historical examples can still contain placeholders. Do not run a blanket substitution across bundled application sources.

Local-only setup

Local execution does not contact dTM when DISTRIBUTED_TM is false. The stock configurator still requires Java and web answers. To configure manually for a local deployment, review its substitution list, set installation/tool values in lib/CTI_global.env and conf/default.conf, and ensure scripts' Perl interpreter paths exist. Also set the installation and scratch settings in dtm/lib/DTM_global.env and dtm/conf/dTM_conf.xml: local runs bypass the dTM server but still use its configuration/library code to resolve machine scratch storage. Set CTI_GROUPS explicitly in your option file. This is a manual alternative, not a separate supported configuration switch.

Use the local run example to inspect settings before executing a small unit. Local runs need neither a running dTM server nor a web server. Do not start services simply to display the docs.

Optional services

Dashboard hostnames, web roots and deployed filesystem paths are organization-specific configuration for proprietary servers, private infrastructure or on-premises clouds. Keep the distributed source unconfigured and set these values in the organization's deployment copy. The optional dashboard-to-Terminal setup documents each server/Mac setting, same-origin catalogs, reverse-proxy URLs, user-scoped enrollment and rollback. Its CTI_SESSION_LINKS_URL and CTI_SESSION_LINKS_FILE settings belong to the web service's CGI environment; configure.pl does not prompt for them. No particular live server is required to build or review the package.

For dTM worker definitions, native load monitors, Java rebuilding, and the web document root, continue with distributed testing. For application dependencies, inspect the selected unit's tmconfig, Src/Makefile.CTI, and upstream installation notes.

Layout and enrollment

cti_groups/
  Regression/
    tmconfig                 # CHILDREN and regression.pl selection
    myunit/
      tmconfig
      tmconfig.env           # optional pattern-specific settings
      tmconfig.list          # optional multi-source definitions
      Src/
        sample.c
        sample.tmconfig      # optional per-test settings
      Masters/
        sample.out
  Applications/
    tmconfig                 # CHILDREN and application.pl selection
    myapp/
      tmconfig
      Src/
        Makefile.CTI
        ...

A Src/ subdirectory identifies a unit. Add new units to the parent group's CHILDREN list for group-wide runs. A direct unit selection works without parent enrollment. Preserve filename case, especially C .c versus C++ .C.

Regression tests

The regression driver discovers individual sources by the configured extension/language mapping. Put a single-source test in Src/. Add its runtime master under the configured MASTER_FILE_PATH; Regression/tmconfig sets that path to ../Masters, relative to Src.

A minimal test that produces no output can use an empty master:

int main(void) { return 0; }

For sample.c, place an empty Masters/sample.out. CTI's regression output padding is enabled by default; set RUN_TESTS_PAD_OUTPUT=false in Src/sample.tmconfig when the master should contain only raw program output. Verify the captured output before accepting the master.

For a compile-only test, add RUN_TESTS=false to its .tmconfig; also set LINK_TESTS=false if no link step is intended. A negative compile test uses CT_NEG=true. To compare diagnostics, enable CT_DIFF=true and provide the appropriate .err master, or use ERROR_MASTER_EMPTY=true if an empty diagnostic master is intended.

For negative runtime tests, configure RUN_TESTS_NEG=true and runtime exit checking, then verify a deliberately unexpected zero exit as well as the expected rejection. The FT11 capture finds that the legacy outer script can overwrite ExecBadPass with SuccessExec when the run phase exits zero. A final pass alone is insufficient to validate this oracle.

For multi-source tests, create Src/<name>.list listing source files, or a unit-level tmconfig.list with records such as:

joined: first.c second.c

Inspect readListFile.pm for list syntax. collectTests.pm prevents these component sources from also running as independent tests.

Master names start with the test base name and the configured suffix (out or err by default). RUNTIME_OUTPUT_QUALIFIERS and ERROR_OUTPUT_QUALIFIERS can insert option values into the name. locateMaster.pm defines the lookup order and the special Fortran handling of the COMPILER_VERSION qualifier.

Use SELECTIONS for the unit and TESTS for a specific test filename. Run locally with CLEAN=false, inspect compile/link/run commands, and confirm that the intended failure or output comparison is exercised before adding it to broad selections.

Application wrapper contract

The application driver operates on one application unit, populates a work directory, customizes options, and generates scripts calling GNU make. Set the wrapper filename in the application's tmconfig:

MAKEWRAPPER=Makefile.CTI

The implementation adds -f only when MAKEWRAPPER is set. Otherwise GNU make uses its normal makefile discovery. There is no hardcoded M.hp.TAHOE default in this driver.

The normal compile stage invokes the make target compile; the normal execution stage invokes validate. A successful validation must return zero and leave compare.results present and empty. A missing file produces an execution failure; a nonempty file produces an output-difference failure. Separate run, compare, and clean targets are useful wrapper conventions; they are not each independently invoked by the normal two-stage driver path.

The driver passes CC, CXX, FC, AR, EXTRA_FLAGS, language-specific EXTRA_CFLAGS/EXTRA_CXXFLAGS/EXTRA_FFLAGS, EXTRA_LIBS, SIMULATOR, and GMAKEROOT when defined. EXTRA_FLAGS includes data-mode and optimization settings. Wrappers must actually forward those flags to the upstream build; assigning CC alone does not prove the compiler used the intended options.

A simple wrapper around a configure/make project can follow this pattern. Recipe indentation must be tabs:

export CC
export CFLAGS = $(EXTRA_FLAGS) $(EXTRA_CFLAGS)

compile:
	./configure
	$(MAKE) -f Makefile

validate:
	rm -f compare.results
	$(MAKE) -f Makefile check
	: > compare.results

clean:
	$(MAKE) -f Makefile clean

Only create the empty marker after validation succeeds. Remove stale markers first. A failed upstream check must propagate failure rather than being hidden by an unconditional successful command. For a real bundled example, see GSL's wrapper.

APPLICATION_SETUP_HOOKS customizes work-directory preparation. APPLICATION_RUN_HOOK supplies a script generator for specialized runs; it receives the unit name and output-script filename. Performance templates use this mechanism. Use the declared hooks and driver code to establish argument and exit-code contracts.

Import and dependencies

Import a clean source tree, not a previously built directory. Retain upstream notices and record any portability patches. Ensure configuration respects the selected compilers and flags, and arrange for tests to run without interactive input. Avoid fixed scratch filenames that collide across concurrent jobs. Set TIME_LIMIT to a justified value for larger builds.

The bundled application units are Applications/gsl-1.14 and Applications/hmmer-2.3.2; Perf/ex1 is a performance example. Dependencies come from each unit's wrapper and upstream source, not from a package dependency installer. Application runs also require the hardcoded Linux GNU make path described in installation.

Legacy add-test tools

TM.pl does not implement an add command. The older import tool is bin/www/addtest.pl, with a web form at www/cgi-bin/addtest.cgi. Its parser requires -CTI_GROUPS to specify the absolute test root. It includes SVN/ClearCase-oriented check-in helpers and is not a Git-aware replacement for editing a working tree. Use the manual layout workflow above for this Git checkout; review the tool's implementation and dry-run behavior before using it in a configured legacy repository.
